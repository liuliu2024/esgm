## 2 三端角色和页面

| 界面 | 谁进入 | 主要信息 | 可执行动作 |
|---|---|---|---|
| 企业前台 | 在组织内有客户角色的发起人 | 本人受理单、状态、最新退回理由和办理历史 | 选择场景、填写用途、提交、补正重提。没有待办时引导新建 |
| 专业作业台 | 受权组织内的复核人 | 已提交及已处理的任务、当前版本、原始用途、补正及历史决定。可办理的待审项优先 | 对提交版批准或退回，退回必填理由。自己发起的事项可查，无自审动作 |
| 管理端 | 组织管理员 | 当前组织的审计和请求关联 | 查阅审计。配置和成员授权列入下一轮 |

界面只展示当前角色可办的事。任务阶段、主要动作与退回原因放在同一上下文。接口对无权限、数据不存在和过期版本分别返回可处理的状态。使用 API 自动化的 Agent 与界面走同一权限校验。

## 3 任务状态和异常

| 当前状态 | 动作 | 执行人 | 输入和条件 | 新状态及审计 |
|---|---|---|---|---|
| 无 | 新建 | 客户 | 当前组织、发布场景版本、用途 | 草稿，版本 1，`created` |
| 草稿 | 提交 | 发起人 | 预期版本等于当前版本 | 待复核，版本加一，`submitted` |
| 待复核 | 批准 | 同组织独立复核人 | 预期版本一致 | 已批准，版本加一，`approved` |
| 待复核 | 退回 | 同组织独立复核人 | 预期版本一致，说明退回原因 | 已退回，版本加一，`returned` |
| 已退回 | 补正重提 | 发起人 | 预期版本一致，填写本次补正说明 | 待复核，版本加一，`submitted`，审计保存本次补正 |

原始用途和场景发布版本保持可查。补正重提保存新的补正说明，清除当前退回状态，原退回原因仍在历史中。批准表示受理信息通过复核。旧版本提交或重复决策返回 409，前端提示刷新并保留未提交文本。状态和审计在同一事务内提交，失败时同时回滚。

## 4 接口与数据

| 用例 | API | 请求 | 结果 |
|---|---|---|---|
| 客户或专业任务列表 | GET `/v1/{customer|professional}/cases` | `orgId`，可选 `limit, cursor` | `{cases, nextCursor}`。客户只看本人，专业待审核优先。各项附 `nextAction` |
| 任务详情和历史 | GET `/v1/{customer|professional}/cases/:id` 与 `/history` | `orgId` | 受理单和按修订排序的状态历史，包括理由和补正 |
| 新建 | POST `/v1/customer/cases` | `orgId, scenarioReleaseId, purpose` | 201 草稿 |
| 首次提交 | POST `/v1/customer/cases/:id/submit` | `orgId, revision` | 200 待复核 |
| 退回补正 | POST `/v1/customer/cases/:id/resubmit` | `orgId, revision, correctionNote` | 200 更新版本的待复核受理单 |
| 复核 | POST `/v1/professional/cases/:id/review` | `orgId, revision, decision`，退回时附 `reason` | 200 已批准或已退回 |
| 审计 | GET `/v1/admin/organizations/:orgId/audit` | 分页参数 | 本组织的状态、版本、理由、补正及操作关联 |

入口校验请求结构、标识、版本和非空业务文本。权限来自可信身份上下文及组织授权。400 表示输入不合规，401 表示身份无效，403 表示动作权限不足，404 表示资源不可见，409 表示版本或状态冲突。错误以稳定代码供 UI 和 Agent 区分。

数据库维护 `workspace`、`organization`、`org_grant`、`scenario_release`、`case_intake` 和 `audit_event`。组织、任务及场景采用租户复合键。新增补正采用增量迁移；旧行保留原有数据和空补正字段。任务现状与历史审计分别保存，正式生产环境使用独立的非所有者运行账号。

## 5 验收和后续优先级

1. **数据库**：既有迁移已执行时增量迁移可重跑。验证原始用途、场景版本、旧退回原因与多次补正均可查。无上下文、跨组织及跨租户访问被拒绝。
2. **服务**：客户列表只返回本人，复核列表只返回有权任务。走两轮退回、重提后批准，并验证过期版本、自审、空理由或补正及撤权。
3. **界面**：客户能够找到退回原因和补正入口，专业作业台能够辨认当前补正及旧记录，管理页面能定位审计。用演示数据验证动作与 API 一致，区分演示身份和正式身份。
4. **生产**：正式身份映射、真实 PostgreSQL 多连接隔离、迁移和恢复仍是放行条件。阶段验收继续推进，未验证项目单列。

下一轮优先接入证据文件元数据和访问权限，再接结构化数据采集、核算快照与报告签发。各轮先写最小验收规格，再开发和测试。北京时间 2026 年 11 月 6 日 09:00 为本轮检查节点。当前范围提前验收后，按工程规则从开源及国内可追溯资料选择下一项改进。
