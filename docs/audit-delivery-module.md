# 审核交付开发包

对应详细功能需求说明书 AUD01–04、RPT04。模型计算已实现范围的本机复验见晨间验收材料。审核交付沿用现有企业受理、提交修订、专业复核、稿件和具名交付，不复用它们的状态来代表正式发布。

| 需求 | 已有底座 | 本包新增与验收 |
| --- | --- | --- |
| AUD01 提交审核 | 受理提交和补正已固定版本、材料与活动，专业审批和报告复核各有记录 | 专业人员按同一提交核对原件、数据缺项、适用规则和差异。结论能定位人员、时间、范围及版本 |
| AUD02 问题整改闭环 | 有整单退回理由、补正说明及修订历史 | 新增问题级往返。专业人员发起、企业负责人答复、独立专业人员关闭或要求再补。清楚显示严重性、到期和变更历史 |
| AUD03 锁期与重开 | 已冻结快照和报告，当前提交与历史提交可区分 | 单独定义期间锁定和授权重开。重开产生新提交及新审核，旧结果和文件可查。绕过页面直接写锁定期间须被拒绝 |
| AUD04 外部机构协作 | 具名采购方交付可登记人工凭证 | 独立设计任务授权、限定资料清单、问询、到期撤权及外部结论归档。权限扩大按项目约束另行上报 |
| RPT04 报告审核及发布 | 内部报告有水印、独立复核、版本和受控 HTML/PDF | 正式发布单独配置资格和阻断条件。关键整改问题关闭之前禁止正式发布；批准、发布、替代各留记录 |

## AUD01 提交版本复核摘要

专业案卷「材料与范围」随提交版本显示固定材料数、活动留存状态和条数、规则判断、因子版本及未关闭问题。相比上一次实际提交，按材料标识对比回执，按月份和来源对比活动修订，分别给出新增、移除和变更计数。旧版未采集活动时，活动差异为空，界面与已采集零条明确区分。

`GET /v1/professional/cases/:caseId/revisions/:revision/review-summary?orgId=…` 复用现有组织复核权限，未知提交返回 404。所有数字取自选中的提交及其历史版本，问题按发起时的修订统计。摘要供复核定位，原件、规则、计算及问题详情仍可通过原入口打开。

## 首片 AUD02 问题级整改

本片覆盖同一受理任务已提交版本的内部问题往返。问题与整单退回并存。回复或关闭问题不推进受理、报告或外发状态。

### 角色与状态

- 有权复核该组织任务且非任务发起人的专业人员创建问题。问题固定原始提交修订。标题、说明、严重性及到期日必填，可附该提交已固定的证据引用。责任人首片使用任务发起人。
- 企业任务发起人可答复问题，专业人员可要求补充或在已有答复后关闭。专业人员要求补充时说明原因。关闭需要结论。原问题及历次答复、补充要求和关闭记录按时间读取。
- 状态为 `open → answered → closed`，或从 `answered` 经要求补充回到 `open`。逾期由未关闭状态与到期日计算。任务补正不会覆盖旧问题，企业与专业端按发起时的修订查看。
- 确定性阻断发生在写入边界。跨任务证据、跨组织写入、撤权、自审和错误状态均须拒绝。界面显示当前人可用动作。

### 数据与接口

- 问题记录包含租户、组织、任务、问题 ID、原提交修订、标题、说明、严重性、到期日、责任人和发起人。材料引用复用受理提交证据的复合键。状态变更与追加事件同事务保存，事件包括动作、参与者、请求标识、原因及时间。
- `GET /v1/{customer|professional}/cases/:caseId/review-issues?orgId=…` 返回 `{canOpen, items}`。问题包含 `issueId`、`submissionRevision`、`status`、`version`、`overdue`、`nextActions` 和有序 `events`。
- 专业人员用同路径 `POST {orgId,submissionRevision,title,description,severity,dueDate,evidenceId?}` 发起。严重性为 `low`、`normal` 或 `critical`，到期日为北京时间日期 `YYYY-MM-DD`。企业使用问题 ID 下的 `/reply`，专业端使用 `/request-follow-up` 或 `/close`，请求均为 `POST {orgId,expectedVersion,note}`。状态或版本变化返回 409；刷新后按返回的 `nextActions` 操作。
- 企业在办理详情查待答复与历史，专业端在案卷查问题及历次回复。默认显示逾期、严重性和当前动作，展开后可读引用与时间线。

### 首片验收

1. 用合成任务和两个提交版本，由专业人员发起问题、企业答复、专业要求补充、企业再次答复、专业关闭。原修订、引用、责任人和完整事件顺序均可查。
2. 尝试用其他任务证据、另一个组织账号、已撤权账号及自审账号访问或变更。失败应无新事件。关闭后重放状态转换须拒绝。
3. 旧版问题与补正后的新提交可同时查阅。已有受理、天然气重述、内部报告及受控采购方交付路径回归。
4. 正式发布阻断在 RPT04 的发布动作实现。首片先保存和查询关键未关闭问题，不引入外部协作权限或正式签发能力。

## AUD03 锁期与重开

首轮锁定粒度为已批准任务及其申报年度。沿用原任务在批准后禁止修改台账、材料和已固定结果的写入边界。以只读预览、独立授权、新修订交接三个步骤实施。

1. `GET /v1/{customer|professional}/cases/:caseId/reopen-impact?orgId=…` 仅对明确申报年度的已批准任务返回锁定年度、批准和原提交版本、固定材料与活动计数、未关闭关键问题及当前角色有权查阅的关联稿件。未批准、旧任务缺年度或没有对应提交均返回 409。预览不改变任何记录。
2. 企业发起人指定原批准版本并提交重开原因。独立专业人员核对该版本的影响后批准或退回，退回理由必填。记录申请人、审阅人、申请和审批时间、原版本以及决定。原任务保持锁定。
3. 获批后由原任务发起人创建唯一关联的新草稿。新草稿沿用场景、组织和申报范围，并固定指向原任务、原批准版本和授权记录。后续按新任务独立提交和审核。旧稿、快照及历史记录仍从原任务访问。

接口以 `/v1/{customer|professional}/cases/:caseId/reopen-requests` 为根。两端 `GET ?orgId=…` 读取申请及可用动作。企业 `POST {orgId,approvedRevision,reason}` 发起；专业端 `POST /:requestId/review {orgId,decision,reason?}` 审批；企业 `POST /:requestId/draft {orgId}` 创建草稿。后者首次返回 201，重放返回同一任务及 200。专业端在新草稿提交前看不到它。

开发验收需覆盖原任务直接写入继续拒绝、未授权创建拒绝、重放不重复、新草稿独立审批、角色撤权及跨组织拒绝。数据库与接口已接通，企业和专业页面后续接入。

## RPT04 发布条件核对

专业人员在「报告复核」打开稿件时可查发布条件。接口为 `GET /v1/professional/cases/:caseId/internal-report-drafts/:draftId/release-readiness?orgId=…`，复用独立专业角色、任务和报告原有可见范围。

逐项显示任务是否已批准、是否引用当前有效提交、申报范围是否留存、覆盖是否完整、是否独立复核、是否有未关闭关键问题和正式报告资格。关键问题按同一任务统计，补正提交不会自动清除旧问题。返回 `{draftId,canPublish,criticalIssueCount,checks}`，检查项包含稳定编码和布尔结果。

本地首片为只读。即使内部复核通过，现有稿件的正式报告资格仍为假，界面无正式发布动作。正式批准、发布及替代待其权限与运行边界明确后接入。
