# RQ02 B 任务活动台账

依据研发交接 RQ02、附件 DAT03–06 和 AT03/04。当前上线的是无写入的 CSV 预检。以下为批次与入账方案。案例仍以测试数据验收。

## 对象和数据契约

现有受理表提供稳定的 `tenant_id, org_id, case_id`。首期将受理任务作为导入对象，活动自然键为 `(tenant_id, org_id, case_id, period, source)`。一个任务内，同月同类型有一笔活动及其修订链。组织名、场景版本及文件行号均不能替代对象标识。多个受理可能描述同一实际设施，首期结果仅在任务内使用。后续引入正式设施、产品或其他对象标识时，先确认历史任务归属和数据去重，再允许组织级汇总。

沿用四列表头和两种活动类型。月份用该月一日的 `date` 持久化，接口保留 `YYYY-MM`。原数量及原单位保留输入文本，标准数量保存为无固定舍入的 PostgreSQL `numeric`，接口始终以十进制字符串读写。换算标识固定为 `activity-csv-v1`，首版电力统一为 kWh、天然气保持 m3。按标准量数值比较，`1 MWh` 和 `1000 kWh` 等量。缺值和格式错误留在预检问题里，真实零可入账。合法行标记 `manual_csv`。估算、源记录外部 ID、正式原件和质量关闭另行接入。

## 接口

| 动作 | 请求及结果 |
|---|---|
| 即时预检 | 原 `POST /v1/customer/cases/:id/imports/preview` 保持原语义和响应，未生成批次 |
| 保存批次 | `POST /v1/customer/cases/:id/imports` 接收 `{orgId,csv}`，复用预检解析及权限。返回 `{batchId,previewRevision,status,summary,issues,preview}`。同一任务、模板和源摘要的已存批次返回已有预览或原入账回执 |
| 重预检 | `POST /v1/customer/cases/:id/imports/:batchId/repreview` 接收 `{orgId,previewRevision}`。对同一冻结源按当前活动基线重新分类，生成下一预览修订。更换 CSV 通过新批次完成 |
| 查批次 | `GET /v1/customer/cases/:id/imports/:batchId?orgId=…` 返回最新预览，已提交时同时返回回执 |
| 确认入账 | `POST /v1/customer/cases/:id/imports/:batchId/commit` 接收 `{orgId,previewRevision}`，整批确认当时展示的行和差异。回执固定 `batchId,previewRevision,inserted,corrected,unchanged,committedAt` |

预览的每个有效行标记 `insert`、`correct` 或 `unchanged`，同时记录作为比较依据的活动基线修订。新增行基线为空，更正行展示原活动值和新值，等量的旧值保留原出处。文件内重复、缺值、量纲问题或格式错误仍阻断整批，问题保留原行列和稳定代码。

缺组织角色返回 403，批次或任务不可见返回 404。阻断批次、旧预览或任一行的活动基线变化返回 409 并提示对应修正。入账完成后，获授权的本人以相同批次和修订重试时取得原回执。读取既有回执允许任务已进入复核，新增入账要求任务仍为草稿或退回。

## 表与权限

| 表 | 键和冻结内容 |
|---|---|
| `carbon.ingestion_batch` | 主键 `(tenant_id,org_id,case_id,id)`，复合外键指向现有受理。固定 CSV 摘要、模板版本、创建者、请求 ID 和时间。同任务、模板版本和 SHA-256 唯一。源 CSV 仅限现有小请求上限内的 UTF-8 文本，存放于受限业务表，保留供同源重预检和核对，不进入日志和回执 |
| `carbon.ingestion_preview` | 复合键为批次及 `revision`。附预检状态、问题及合法行的结构化快照。有效行包含源行、原量与原单位、标准量与标准单位、活动基线及动作。规则版本随批次固定。每次重预检追加新修订 |
| `carbon.activity_record_revision` | 复合键为活动自然键及递增 `revision`，追加后不修改。包含本次标准量和原始行值、来源类型、换算版本、批次与预览修订、源行。当前有效行取同一自然键的最高修订 |
| `carbon.ingestion_commit` | 每个批次仅一份，复合外键指向批次及预览修订。持久化回执统计、操作者、确认时间和请求 ID，可查询关联的入账行 |

四张表统一采用租户范围 RLS 及任务归属限制。业务读入口仅开放企业本人，可见性同时依赖有效组织客户角色；撤权后旧 ID 无法读取或确认。优先沿用已有事务上下文及复合外键。提交动作由限定权限的数据库入口追加记录，运行角色不给活动修订、预览或回执直接修改权限。数据库证据由批次、预检及回执保留，日志仅记标识、动作、时间及计数。

## 事务与验收

保存、重预检和确认都先锁同一任务行，再读取活动基线、批次、最新预览和已有回执。任务行也是现有提交状态更新的互斥点，因此能让同任务多批次和受理提交按顺序完成。确认时核对任务权限、可编辑状态及全部基线。预览生成与入账可分请求，入账只使用服务持久化的预览行，不接受外部数量、动作或基线覆盖。新增行写版本 1，更正写当前版本加 1，等量行不追加。任一失败同时回滚整批修订和回执。预检和入账使用各自的业务记录，受理状态及受理审计历史保持原语义。

验收须覆盖两种活动及真实零，测试空值、错单位、重复和等量换算。对更正先查看旧值和新值，确认后核对旧修订仍可查。模拟两个批次针对同一活动版本入账，后确认者得到过期错误，并验证无部分入账。原批次、原修订重放取同一回执。检查他人任务、同租户异组织、跨租户、撤权、已提交任务和旧预览。服务、数据库、合成 CSV 各有独立验证，专业核算前再以经授权的真实样本验收。
